# Phase 999.9: Kie API Credit System - Research

**Researched:** 2026-04-02
**Domain:** Credit-based API gating, per-model cost tracking, admin balance management
**Confidence:** HIGH

## Summary

This phase introduces a pre-paid credit system that gates ALL Kie.ai API calls across three distinct call paths: the video route (ContentPackage), the reels pipeline (ReelsJob), and the product ads pipeline (ProductAdJob). The system replaces the existing daily USD budget cap (`VIDEO_DAILY_BUDGET_USD`) with a persistent balance-based approach using abstract credit units ($7 USD = 1000 credits).

The codebase currently has three separate Kie API call paths, only one of which (video route) writes to `api_usage`. The reels pipeline stores cost on `ReelsJob.cost_usd/cost_brl` directly, and the ads pipeline stores cost on `ProductAdJob.cost_brl`. Neither the reels nor ads paths have any pre-call budget check. The credit system must intercept ALL three paths with a hard pre-check before any Kie API call is made.

**Primary recommendation:** Create a centralized `CreditService` (not a repository -- it orchestrates balance check + deduction + logging atomically) that wraps all Kie API calls. Place the pre-check at the point where `KieSora2Client` and `KieMusicClient` are instantiated/called, not as HTTP middleware (too coarse for background tasks). New `user_credits` and `credit_logs` tables in separate migration.

### Pattern 1: Centralized Credit Service
**What:** A single `CreditService` class handles all credit operations atomically: check balance, deduct, log, and refund on failure.
**When to use:** Every Kie API call path (video, reels, ads).
**Why not middleware:** Background tasks (reels, ads) don't go through HTTP middleware. The credit check must happen at the service layer.
**Example:**
```python
class CreditService:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def check_and_deduct(
        self, user_id: int, model_id: str, duration: int,
        job_type: str, job_id: str,
    ) -> int:
        """Pre-check balance, deduct credits, log the call.
        Returns credits consumed. Raises InsufficientCreditsError if blocked.
        """
        cost = self.compute_credit_cost(model_id, duration)
        credit = await self._get_or_create_balance(user_id)
        if credit.balance < cost:
            await self._log(user_id, model_id, duration, cost, "blocked", credit.balance, job_type, job_id)
            raise InsufficientCreditsError(balance=credit.balance, required=cost)
        credit.balance -= cost
        await self._log(user_id, model_id, duration, cost, "success", credit.balance, job_type, job_id)
        await self.session.flush()
        return cost

    async def refund(self, user_id: int, credits: int, reason: str, job_id: str):
        """Refund credits on failed generation (after deduction)."""
        ...

    async def top_up(self, user_id: int, amount: int, admin_id: int, note: str):
        """Admin manual credit addition with audit trail."""
        ...

    @staticmethod
    def compute_credit_cost(model_id: str, duration: int) -> int:
        """Map model + duration to credit cost from CREDIT_COSTS dict."""
        ...
```

### Pattern 3: Session Handling in Background Tasks
**What:** Background tasks in reels and ads use `get_session_factory()` to create independent DB sessions (request session unavailable).
**Implication for credits:** The `CreditService` must accept a session parameter, and background tasks must create their own CreditService instance with the factory session.

### Anti-Patterns to Avoid
- **HTTP middleware for credit checks:** Background tasks bypass HTTP middleware entirely. Credit checks must be at the service/function level.
- **Deducting after the API call:** If deduction happens after the call, a race condition allows overspend. Deduct BEFORE, refund on failure.
- **Sharing credit check with api_usage:** The CONTEXT.md explicitly says credit_logs is separate from api_usage. Don't merge them.
- **Float credits:** Use integer credits to avoid floating point rounding issues. The $7=1000 rate already produces clean integers for most models.

## Per-Model Credit Cost Mapping

### Methodology
Kie.ai pricing page uses dynamic JavaScript rendering and cannot be scraped directly. The existing `VIDEO_MODELS` dict in `config.py` has verified BRL prices. I derived Kie.ai credit costs by reversing: `USD = BRL / 5.75`, then `kie_credits = USD / 0.005`.

Kie.ai system: $0.005/credit (200 credits/$1, 1000 credits/$5).
App system (user decision): $0.007/credit (1000 credits/$7).

**Confidence: MEDIUM** -- BRL prices in config.py were manually verified against Kie.ai pricing at time of entry (Phase 999.1, Phase 421). Kie.ai may have changed prices since. The planner should include a task to verify prices at implementation time.

### Duration Snapping
The existing `KieSora2Client.create_task()` already snaps duration to the nearest valid value for each model. The credit cost lookup should use the same snapping logic: find closest valid duration in `CREDIT_COSTS[model_id]`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Concurrent balance modification | Optimistic locking with Python dicts | SQLAlchemy row-level `SELECT ... FOR UPDATE` | Race conditions between concurrent API calls |
| Credit cost lookup | Hardcoded if/elif per model | Dict-based lookup with closest-duration snap | Already have this pattern in `compute_video_cost_brl()` |
| Audit trail | Custom logging to file | `credit_logs` table with structured fields | Queryable, filterable, consistent |

## Common Pitfalls

### Pitfall 1: Race Condition on Balance Deduction
**What goes wrong:** Two concurrent Kie API calls both read balance=50, both pass the check, both deduct 30, resulting in balance=-10.
**Why it happens:** Default SQLAlchemy reads don't lock the row.
**How to avoid:** Use `SELECT ... FOR UPDATE` when reading balance for deduction. In SQLAlchemy:
```python
stmt = select(UserCredit).where(UserCredit.user_id == user_id).with_for_update()
```
**Warning signs:** Negative balances appearing in production.
**Note:** SQLite does not support `FOR UPDATE`. The project uses SQLite for local dev and MySQL for production. For SQLite, rely on the single-writer serialization. For MySQL, `FOR UPDATE` is critical.

### Pitfall 2: Credit Deduction Without Refund on Failure
**What goes wrong:** Credits are deducted before the Kie API call, but the call fails (timeout, 500, bad prompt). User loses credits for nothing.
**Why it happens:** No refund mechanism after deduction.
**How to avoid:** After `KieSora2Client` returns None/raises, call `credit_service.refund()`. Log the refund in `credit_logs` with status="refunded".
**Warning signs:** Users complaining about lost credits despite no video generated.

### Pitfall 3: Reels Pipeline Multi-Scene Credit Check
**What goes wrong:** A reel with 5 scenes checks credit for scene 1, but runs out at scene 3. Three scenes generated, two wasted, partial result.
**Why it happens:** Credit check is per-scene instead of pre-computed for all scenes.
**How to avoid:** In `ReelsPipeline._generate_clip()`, the pipeline generates multiple clips via `asyncio.gather()`. The credit pre-check should estimate total cost for ALL scenes before starting any. Deduct total upfront, refund unused if some fail.
**Warning signs:** Partially generated reels with insufficient credits mid-way.

### Pitfall 4: Background Task Session Scope
**What goes wrong:** Credit deduction happens in the HTTP request session, but the Kie API call happens in a background task with a different session. If the background task fails, the original session's deduction can't be rolled back.
**Why it happens:** Background tasks use `get_session_factory()` for independent sessions.
**How to avoid:** Deduct credits in the background task session, not the request session. The HTTP endpoint only does a read-only balance check (enough credits?). The actual deduction happens in the background task where the API call occurs.
**Warning signs:** Credits deducted but API call never made (request session committed, background task crashed before starting).

### Pitfall 5: Existing Budget System Conflict
**What goes wrong:** The existing `_check_budget()` in video.py still enforces `VIDEO_DAILY_BUDGET_USD`, blocking calls even when credits are available.
**Why it happens:** Two budget systems running in parallel.
**How to avoid:** Replace `_check_budget()` with credit check. Remove or feature-flag the daily USD budget. The credit system supersedes it.
**Warning signs:** 429 errors from old budget system despite having credits.

### Credit Pre-Check in Background Task (Video Route Pattern)
```python
# In _generate_video_task() -- src/api/routes/video.py
async def _generate_video_task(content_package_id, duration, ..., user_id, model):
    session_factory = get_session_factory()
    async with session_factory() as session:
        credit_svc = CreditService(session)
        try:
            credits_consumed = await credit_svc.check_and_deduct(
                user_id=user_id,
                model_id=model or VIDEO_MODEL,
                duration=duration,
                job_type="video",
                job_id=str(content_package_id),
            )
        except InsufficientCreditsError:
            # Mark package as blocked, commit, return
            pkg.video_status = "blocked"
            pkg.video_metadata = {"error": "Insufficient credits"}
            await session.commit()
            return

        # Proceed with Kie API call...
        client = KieSora2Client()
        gen_result = await client.generate_video(...)

        if not gen_result:
            # Refund on failure
            await credit_svc.refund(user_id, credits_consumed, "generation_failed", str(content_package_id))
            ...
```

### Admin Top-Up Endpoint
```python
@router.post("/admin/top-up", summary="Admin: add credits to user")
async def admin_top_up(
    user_id: int = Body(...),
    amount: int = Body(..., gt=0),
    note: str = Body(""),
    current_user=Depends(get_current_user),
    session: AsyncSession = Depends(db_session),
):
    if current_user.role != "admin":
        raise HTTPException(403, "Admin only")

    credit_svc = CreditService(session)
    new_balance = await credit_svc.top_up(user_id, amount, current_user.id, note)
    await session.commit()
    return {"user_id": user_id, "credits_added": amount, "new_balance": new_balance}
```
