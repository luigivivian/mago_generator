# Phase 999.9: Kie API Credit System — Context

**Gathered:** 2026-04-02
**Status:** Ready for planning

<domain>
## Task Boundary

Pre-paid credit system that gates all Kie API calls, tracks per-model costs with real pricing from kie.ai, and provides admin controls for balance management. Includes a dedicated logs page and admin top-up form.

</domain>

<decisions>
## Implementation Decisions

### Credit Model
- **Abstract credit units**, not raw BRL
- Conversion rate: **$7 USD = 1000 credits**, converted to BRL at current exchange rate
- Each Kie model has a credit cost derived from its real USD price on kie.ai/pricing
- Replaces the existing daily budget system with a balance-based approach
- New `user_credits` table: `user_id`, `balance` (integer credits), `updated_at`

### Blocking Behavior
- **Hard block before EVERY Kie API call** — pre-check credit balance
- If insufficient credits: show inline error with remaining balance and cost required
- No API call is made when balance is insufficient — prevents debt
- No negative balances allowed
- Applies to: reels clips, product ads, video generation — any path that calls Kie.ai

### Logs & Monitoring
- **New dedicated page** (`/credits` or `/logs`) — separate from existing dashboard
- **Per API call granularity** — each Kie.ai call = one log row
- Log fields: timestamp, model, duration, credits consumed, status (success/failed/blocked), balance after, job reference (reel/ad job_id)
- Filterable by date range and model
- All calls logged — including blocked calls (insufficient credits)
- New `credit_logs` table for this (NOT reusing `api_usage` — different purpose)

### Admin Top-up
- **Admin-only manual form** — no Stripe integration for now
- Simple form: select user, enter credit amount, optional note
- Creates an audit trail entry in `credit_logs` with type "top_up"
- Top-up page at `/admin/credits` or section in existing admin area

### Claude's Discretion
- Per-model credit costs: research current kie.ai/pricing and map each model to credit cost based on $7=1000 credits rate
- Schema design for `user_credits` and `credit_logs` tables
- Where to place the pre-check logic (middleware vs per-endpoint)
- How to handle the existing `api_usage` table — keep for analytics, credit system is separate

</decisions>
